SDLC Agents Loop

What this is

This system takes a feature request from intake to testing through a coordinated loop of specialized agents. One orchestrator drives the lifecycle. Each agent owns a narrow responsibility and writes visible artifacts into a shared workspace.

The core idea is simple: instead of hiding work inside one black-box agent, split the SDLC into explicit roles and let them coordinate through a shared filesystem and a small state machine.

The architecture at a glance

End-to-end flow

Feature Request→ Product Manager→ Architect→ Project Manager→ Developer→ Code Reviewer→ Tester→ Archive

Every stage produces a concrete artifact: PRD, task list, architecture doc, code, review, and test report. That makes the pipeline inspectable and easy to debug.

Control plane

The orchestrator is the only component responsible for routing. It is intentionally not another planning agent. It just reads state, triggers the right worker, waits for completion, and advances the lifecycle.

workspace/ is the shared root

One of the most interesting design choices here is that the runtime workspace behaves like a miniature filesystem root for the agent ecosystem. The agents do not pass messages through an abstract broker. They coordinate through well-known directories and control files.

workspace/ ├── user-input/ # incoming feature requests ├── plan/ │ ├── prds/ │ ├── tasks/ │ └── architecture/ ├── code/ ├── review/ ├── reports/ ├── archive/ ├── state/ └── logs/
This is why the system is so easy to inspect live during a demo. You can literally show where the feature is, what artifact was produced, and which agent owns the next move.

Why this matters

  • There is one active phase at a time.
  • Progress is explicit, not implicit.
  • Failures stop the loop instead of creating silent drift.
  • The lifecycle is easy to reason about and easy to explain.

State files

  • current-state
  • current-feature
  • phase-start-time
  • trigger-{agent} / done-{agent}
  • review-result, test-result, error-message

How would you use it

Start the loop

make build make start

Submit a feature

Monitor

make status make logs-orchestrator AGENT=[agent-name] make logs-agent make plan-view make review-view make report-view

Recover

cat workspace/state/error-message make reset-state

What makes it strong

Transparency

You can inspect almost every step directly from the filesystem and logs.

Separation of roles

Each agent has one job, which keeps prompts focused and artifacts structured.

Low coordination cost

No heavyweight orchestration stack is required to get an end-to-end loop working.

What needs maturity

Current tradeoffs

  • Polling introduces latency.
  • Filesystem coordination needs discipline and cleanup.
  • There is a hard stop on timeout, which is safe but manual.
  • Parallel execution and prioritization are still limited.

Natural next steps

  • Idempotent triggers and retries
  • File locking and race-condition protection
  • Support for multiple concurrent features
  • Approval gates, policies, and dashboarding
This is already a compelling prototype architecture. The next step is not changing the idea. The next step is operational maturity.

Now the bigger idea: an operating system for agents

Today this is an SDLC multi-agent pipeline. But you can also look at it as an early sketch of an operating system for agents.

In this system

  • The orchestrator decides what runs next
  • The feature request is the work unit
  • The state machine defines lifecycle transitions
  • workspace/ is the shared root where coordination happens
  • Well-known files act as control signals
↔

In operating system terms

  • The kernel schedules and coordinates
  • A process carries work through the system
  • The process lifecycle tracks running state
  • The filesystem root exposes structured coordination surfaces
  • Control files and descriptors expose system state
The orchestrator plays the role of a kernel, the feature request is the process, the state machine is the process lifecycle, and workspace/ is the shared filesystem root where agents coordinate through well-known directories and control files.

In other words, what we have today is not just a pipeline. It is the beginning of a model for how agents could coexist inside a common runtime.

Three takeaways

Simple parts

Containers, prompts, files, and a small state machine are enough to build a working autonomous SDLC loop.

Clear visibility

The biggest advantage is transparency. Almost everything is visible, inspectable, and explainable.

Bigger future

The deeper value may be the architecture pattern: a reusable OS-like framework for agents.
